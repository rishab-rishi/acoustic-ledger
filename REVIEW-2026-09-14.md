Two things only reproduce in a sandbox and are **not** bugs in your code:

- `tsc --noEmit` errors with `Cannot find name 'LayoutProps'` on a tree with no

  not. If you ever build in a locked-down CI, switch to `next/font/local`.

## Priority 1 — fix before the next deploy

### 1. Next.js 16.3.0 has two unauthenticated RCE advisories

`npm audit` flags one **critical**:

- GHSA-p293-qw3h-jr36 — unauthenticated RCE on Windows-hosted servers
- GHSA-2xp9-vwfh-vxw4 — unauthenticated RCE in the Image Optimization API when
  AVIF is used

Both affect `next` 16.0.0–16.3.2. Fix: `npm i next@^16.3.5 eslint-config-next@^16.3.5`.
While you're there, `npm audit fix` clears the `fast-uri`, `js-yaml`, `sharp`,
`hono` and `qs` advisories without breaking changes.

### 2. `/api/health` is public and leaks deployment detail

`src/app/api/health/route.ts` needs no auth and returns the database host, the
Vercel region, which Neon-style env var names are present, and — on failure —
the raw driver error message and code. That's a free map of your infrastructure
for anyone who guesses the path.

Gate it. Cheapest version:

```ts
export async function GET(req: Request) {
  const token = process.env.HEALTH_TOKEN;
  if (token && req.headers.get("x-health-token") !== token) {
    return new Response(null, { status: 404 });
  }
  // ...
}
```

Or return the bare `{ ok }` publicly and the detailed body only with the token.

### 3. The cart cookie has no `Secure` flag

`src/lib/cart.ts` sets `cart_session` with `httpOnly` and `sameSite: "lax"` but
no `secure`. Over plain HTTP the guest cart token travels in clear text and can
be lifted and replayed to read or mutate somebody's cart.

```ts
(await cookies()).set(CART_COOKIE, newToken, {
  httpOnly: true,
  sameSite: "lax",
  secure: process.env.NODE_ENV === "production",
  path: "/",
  maxAge: THIRTY_DAYS,
});
```

### 4. Nothing is rate limited

There is no throttling anywhere in the tree. Three endpoints want it:

- `registerUser` — unlimited account creation, and it discloses whether an email
  is registered ("An account with that email already exists").
- The credentials sign-in — unlimited password guesses at bcrypt cost 10.
- `POST /api/paypal/capture` — unauthenticated, and each call costs you a PayPal
  API round trip.

On Vercel, `@upstash/ratelimit` + Upstash Redis is about fifteen lines. A fixed
window of ~5/min per IP on auth and ~20/min on capture would do.

### 5. `CLAUDE.md` contradicts `.gitignore` about secrets

`CLAUDE.md` line 56 states "`.env.local` is committed (it holds sandbox-only
secrets)". But `store/.gitignore` has `.env*` with only `!.env.example`
excepted — so it is *ignored*, not committed. Run `git ls-files store/.env.local`
to see which is true in your history.

If it ever was committed, `AUTH_SECRET` is the problem, not the PayPal sandbox
keys: anyone holding it can forge a session JWT with `role: "admin"` against any
deployment reusing that value. Rotate `AUTH_SECRET` and confirm production uses
a different one. Either way, fix the CLAUDE.md line — it will mislead the next
person (or agent) into committing a real secret.

## Priority 2 — will bite as the catalog grows

### 6. The catalog has no pagination and no limit

`searchProducts()` in `src/db/queries.ts` has no `limit`/`offset`, and
`app/(shop)/products/(catalog)/page.tsx` renders every row it returns, each with
its variants. At 38 products that's invisible. At 2,000 it is a multi-megabyte
RSC payload and a page that takes seconds to paint.

Add `limit`/`offset` to `SearchParams`, put `page` in the query string next to
`q`/`category`/`sort` (it belongs in `CATALOG_KEYS` in `src/lib/catalog-url.ts`,
which already gives you shareable URLs for free), and return a total count for
the pager. Cap the page size server-side so a hand-typed `?limit=100000` can't
be used as a cheap DoS.

### 7. Nine foreign keys have no index

Postgres does not index foreign keys automatically. Confirmed against the seeded
database:

```
account.userId        addresses.user_id     cart_items.variant_id
order_items.order_id  order_items.variant_id  orders.user_id
products.category_id  session.userId        variants.product_id
```

Four of those are on hot paths: `order_items.order_id` (every order detail view
and every settlement), `orders.user_id` (the whole `/orders` page),
`variants.product_id` (every catalog row's stock signal), and
`products.category_id` (the category filter). Add them to `src/db/schema.ts` and
generate a migration:

```ts
// products
(t) => [
  index("products_search_idx").using("gin", t.searchVector),
  index("products_category_idx").on(t.categoryId),
]
// variants
(t) => [index("variants_product_idx").on(t.productId)]
// orders
(t) => [index("orders_user_idx").on(t.userId), index("orders_status_created_idx").on(t.status, t.createdAt)]
// order_items
(t) => [index("order_items_order_idx").on(t.orderId)]
```

### 8. Every route is dynamic — nothing is cached

The build output marks all 20 routes `ƒ (Dynamic)`. That's correct for `/cart`,
`/orders`, `/admin/*` and the API, but the product catalog and product detail
pages are public, identical for every visitor, and change only when an admin
edits the catalog — which is exactly the shape ISR is for.

Give `/products` and `/products/[slug]` a `revalidate`, or better, tag them and
call `revalidateTag()` from the admin product actions (which already call
`revalidatePath`). `generateStaticParams` on `/products/[slug]` would prerender
the catalog too. Note the constraint your own CLAUDE.md records: keep prerendered
pages DB-free at build time, or wire the DB into the build.

### 9. `createPendingOrder()` isn't transactional, and orphans rows

Two issues in `src/lib/pending-order.ts`:

- The `orders` insert and the `orderItems` insert are separate statements. If
  the second fails, you get a `pending` order with no line items. Should that
  order ever settle, `settleOrder()` finds no lines, decrements no stock, and
  marks it paid. Wrap both in `db.transaction()`.
- A new `pending` row is written on *every* click of the PayPal button. Abandoned
  checkouts accumulate forever and inflate the admin order list. Either reuse an
  existing `pending` order for the same cart when the contents haven't changed,
  or sweep rows older than ~24h with a cron.

## Priority 3 — smaller things

### 10. `@types/node` was pinned to `^20` while you run Node 22+

Vercel and your local Node are both 22 or newer. This surfaced concretely: it
blocked the Vitest install with a peer conflict. Bumped to `^24` as part of the
test setup.

### 11. Cancelling an oversold order inflates stock

`settleOrder()` clamps with `greatest(stock - qty, 0)`, so an oversell floors
inventory at zero. `cancelOrder()` then restocks the **full** `line.qty`. Sell 5
units of a variant that had 1, then cancel, and stock reads 5 instead of 1.

Rare, but it's silent inventory corruption. Either record the amount actually
decremented on the order item, or refuse to settle when stock is insufficient
instead of clamping.

### 12. `isSandboxPaypal()` substring check is loose

`base.includes("sandbox.paypal.com")` would accept
`https://evil.example.com/sandbox.paypal.com`. It's an env var so it isn't
attacker-controlled, but the whole point of that function is to be a whitelist.
Compare the parsed hostname instead:

```ts
new URL(base).hostname === "api-m.sandbox.paypal.com"
```

### 13. Cart item order isn't pinned

`getCart()` loads `items` with no `orderBy`, so row order is whatever Postgres
returns. I couldn't make it reorder on a small table, but it isn't guaranteed —
after enough updates rows move pages and the cart list can visibly reshuffle
while someone edits quantities. Add `orderBy: asc(cartItems.createdAt)`.

### 14. `registerUser` is read-then-insert

The unique index on `user.email` makes this safe, but two simultaneous signups
for the same address give the loser "Couldn't create your account. Try again."
instead of the accurate message. Catch the unique-violation code (`23505`) and
return the same "already exists" result.

### 15. `slugify("!!!")` returns `""`

`src/lib/format.ts` can produce an empty slug, which would hit the unique
constraint on `products.slug` as a confusing DB error. Pinned in the new tests —
validate for empty in the admin product action and report it as a field error.

## What's good

Worth saying, because it's unusual in a project this size:

- **Settlement is genuinely correct.** The conditional
  `UPDATE ... WHERE status = 'pending'` is the right primitive, the winner is the
  only caller that touches stock, and the capture route trusts neither the
  client's order id nor its amount — both are read back out of PayPal's response
  and compared in integer cents. I tried to break it three ways in the new tests
  and couldn't.
- **The cents discipline holds everywhere.** No float ever reaches a comparison
  that decides whether an order is paid. `paypalAmountToCents` returns `NaN` on
  junk, and `NaN !== totalCents` means garbage fails closed.
- **Authorization is genuinely defense-in-depth**, and the reasoning in
  `lib/admin.ts` about why the proxy matcher isn't enough for Server Actions is
  exactly right.
- **Order items snapshot** name, variant and price and are never joined back, so
  catalog edits can't rewrite history.
- **The demo checkout fence is well designed** — 404 rather than 403, a
  whitelist rather than a blacklist for the sandbox check, and a `DEMO-` capture
  prefix so nothing in the database can be mistaken for a real payment.
- `CLAUDE.md`, `DESIGN.md` and `PAYPAL_SETUP.md` are better than most commercial
  repos have.
