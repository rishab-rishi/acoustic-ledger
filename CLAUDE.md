# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

The Next.js application lives entirely in [store/](store/). The repository root holds only
[docker-compose.yml](docker-compose.yml) (local Postgres) and the deployment docs
[DEPLOY.md](DEPLOY.md) and [PAYPAL_SETUP.md](PAYPAL_SETUP.md). Run every `npm` / `npx` command
from `store/`. On Vercel the project's Root Directory is set to `store`.

The store is a demo storefront — "Acoustic Ledger", a studio-monitor / audio-gear shop — built
in numbered phases (see git history). It was specced around Stripe + Neon; payments were switched
to PayPal and the dev database to local Docker Postgres. [PAYPAL_SETUP.md](PAYPAL_SETUP.md)
explains why.

## Next.js 16 — not the version in your training data

`store/AGENTS.md` (imported by `store/CLAUDE.md`) is regenerated by `next dev` on every run. It
warns that this Next.js has breaking changes to APIs, conventions, and file structure. Before
writing framework code, read the relevant guide under `store/node_modules/next/dist/docs/`.
Concrete example already in the tree: the `middleware` convention is now `proxy.ts` with an
exported `config.matcher`. Commit the AGENTS.md block with your work — deleting it from a diff
only makes `next dev` recreate the uncommitted change.

scripts below + a manual smoke test (the checklist in [DEPLOY.md](DEPLOY.md) §6). Restart

### Diagnostic scripts

Run with `npx tsx scripts/<name>.ts` from `store/`. They load `.env.local` via `scripts/_env.ts`;
`dotenv` does not override an already-set `DATABASE_URL`, so `$env:DATABASE_URL = "..."` before
the command points a script at production without editing any file.

- `scripts/check-db.ts` — is the database reachable, and how far away is it (TLS + latency).
- `scripts/verify-settlement.ts` — proves settlement can't double-decrement stock under duplicate/concurrent delivery. Only needs a seeded DB.
- `scripts/diagnose-paypal-account.ts`, `scripts/inspect-paypal-orders.ts`, `scripts/verify-paypal-order.ts` — PayPal sandbox probes; `inspect-paypal-orders.ts` is the first stop when a browser checkout fails.

### Environment

`store/.gitignore` ignores `.env*` except `.env.example`, so `.env.local` (sandbox-only secrets,
already pointing `DATABASE_URL` at the Docker Postgres) is **not** committed — it must exist
locally (or be provisioned in the deploy environment) before `dev`/`build`/scripts will work.
`.env.example` documents every variable with an empty or placeholder value. `NEXT_PUBLIC_*` values
are inlined at build time. Google OAuth is optional — `auth.ts` only registers the provider when
both `AUTH_GOOGLE_ID` and `AUTH_GOOGLE_SECRET` are set.

Seeded logins: `admin@demo.test` / `admin123`, `customer@demo.test` / `customer123`.

## Architecture

Next.js App Router, all data access through Drizzle ORM (`src/db/`), Postgres. `@/*` maps to
`src/*`. Route groups: `(shop)` is the storefront, `admin` is the dashboard, `api/` holds route
handlers. shadcn components ("base-nova" style, Base UI primitives) live in `src/components/ui/`.

### Auth is split for the edge runtime

- `src/auth.config.ts` — dependency-free half. Session strategy, JWT/session callbacks, and the
  `authorized` callback that gates routes. Safe to import into `src/proxy.ts`, which runs on the
  edge where bcrypt and `pg` can't be bundled.
- `src/auth.ts` — Node-only half: the Drizzle adapter, Credentials + optional Google providers,
  and a `signIn` callback that folds the guest cart into the user's cart.

Sessions are JWT (no session rows are used at runtime despite the adapter creating the table).
`role` (`customer` | `admin`) rides on the token.

### Authorization is defense-in-depth, not just the proxy

`src/proxy.ts` gates `/admin/*` and `/orders/*` **by path**, and its matcher is a hand-maintained
list. Server Actions POST to whatever URL the user is on, so an action used on a page outside the
matcher never passes through the proxy. Therefore authorization also lives with the thing being
protected: `requireAdmin()` (redirects — for pages) and `adminGuard()` (returns an error — for
actions) in `src/lib/admin.ts`. The `admin` layout calls `requireAdmin()` so every page under it
is gated by default; still guard each admin action explicitly.

### Money is always integer cents

Every amount in the DB and in application code is `integer` cents (`*_cents` columns). PayPal
speaks decimal strings — convert **only** at that boundary (`centsToPaypalAmount` /
`paypalAmountToCents` in `src/lib/paypal.ts`) and always compare in cents. No float ever decides
whether an order is paid.

### Cart ownership

A cart belongs to exactly one owner — a signed-in user (`carts.user_id`) or a guest
(`carts.session_token`, backed by the httpOnly `cart_session` cookie). A DB `check` constraint
enforces exactly-one-of. In `src/lib/cart.ts`: `getCartId()` is read-only and safe from Server
Components; `getOrCreateCartId()` mutates the cookie and must only be called from Actions / Route
Handlers. A signed-in user's cart always wins over a stale guest cookie.
`mergeGuestCartIntoUserCart()` runs in one transaction on sign-in, summing quantities and
clamping to stock.

### Checkout & settlement

The flow is deliberately payment-provider-agnostic:

1. `createPendingOrder()` (`src/lib/pending-order.ts`) re-checks stock, computes amounts **from
   the database** (never the client), and writes a `pending` order row with snapshotted line
   items. The order row is created *first* so its id can travel to PayPal as `custom_id`.
2. `createPaypalOrder` action (`src/actions/checkout.ts`) builds the Orders v2 payload
   (`src/lib/paypal.ts`), calls PayPal, and stores the returned `paypalOrderId`.
3. **Primary settlement is the capture route** `src/app/api/paypal/capture/route.ts` (called by
   the PayPal button's `onApprove`). It trusts nothing from the client: the internal order id and
   the amount paid are both read back out of PayPal's capture response, and the amount is checked
   against `order.totalCents` in cents.
4. `src/app/api/webhooks/paypal/route.ts` is the **fallback** for when the browser dies
   mid-capture, plus PayPal's retries. Verification is a network round-trip to PayPal and needs
   the **raw** request body — never parse-and-restringify it.

Both settlement paths call `settleOrder()` (`src/lib/settle-order.ts`), which is idempotent: a
conditional `UPDATE ... WHERE status = 'pending'` means exactly one caller wins the row, and only
that winner decrements stock. This is what prevents the double-decrement under a capture/webhook
race.

Order `order_items` snapshot `productName`, `variantName`, and `unitPriceCents` and are never
joined back to `products` / `variants`, so later catalog edits can't rewrite order history.

### Demo checkout fallback

`src/lib/demo-checkout.ts` + `src/app/api/demo/checkout/route.ts` place a real, `paid` order
without contacting PayPal — insurance for live demos when the sandbox misbehaves. Fenced three
ways: the route **404s** unless `DEMO_CHECKOUT_FALLBACK=1`; it refuses unless `PAYPAL_API_BASE`
is recognisably the sandbox (whitelist, so a live config can never self-settle); every order it
creates carries a `DEMO-` capture id. Never use it to verify the PayPal integration works.

### Other conventions

- **Server Actions return an `ActionResult`** (`{ ok: true, notice? } | { ok: false, error }`)
  instead of throwing — Next redacts thrown Action errors to a generic digest in production, so
  anything the user must read has to be a return value.
- **Full-text search** uses a Postgres `tsvector` generated column on `products` with a GIN index
  (`src/db/schema.ts`), queried in `src/db/queries.ts`.
- **Catalog filters live in the URL query string** (`q`, `category`, `min`, `max`, `sort`), built
  via `catalogHref()` in `src/lib/catalog-url.ts` — so back button, reload, and pasted links all
  reproduce the same result set. No filter state in components.
- **Builds must not touch the database.** `src/app/not-found.tsx` is `export const dynamic =
  "force-dynamic"` because it (and the header/footer it mounts) reads categories, which otherwise
  makes `next build` require a reachable DB. Keep new build-time-prerendered pages DB-free.
- Admin queries and mutations are isolated in `src/db/admin-queries.ts` and
  `src/actions/admin-*.ts`.
